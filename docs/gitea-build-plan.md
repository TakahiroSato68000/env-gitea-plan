# Gitea 導入および Windows ビルド環境 構成方針メモ

## 1. 目的

古い Windows アプリ開発向けに、閉域寄りでも運用可能なソース管理・ビルド環境を整備する。

本メモでは、初期導入時の構成方針、および将来の拡張前提を整理する。

---

## 2. 採用方針

- ソース管理は **Gitea** を採用する
- Gitea は **Windows 上の WSL2 Linux 環境** で稼働させる
- コンテナ実行には **Linux 側 Engine** を利用する
- **Docker Desktop は既知の選択肢であるが、今回はライセンス面の整理を簡潔にするため採用しない**
- ビルド処理は **Windows 側** で実施する
- NuGet パッケージは **共有フォルダ** から供給する
- 初期は **1 台構成で実証検証** を行う
- 将来的には **ビルド実行環境を別マシンへ分離** する

---

## 3. 採用理由

### 3.1 Gitea を採用する理由

- self-hosted 型の Git サーバーとして導入しやすい
- Git によるソース管理を前提とできる
- 将来、必要に応じて他製品へ移行する余地を確保しやすい
- 初期段階では、機能を絞って構成を単純化しやすい

### 3.2 WSL2 上の Linux 環境を使う理由

- Gitea を Linux 系環境で扱いやすい
- Windows 1 台構成でも、サーバー機能とビルド機能を段階的に整理しやすい
- 初期導入時のサーバー構築を簡略化しやすい

### 3.3 Docker Desktop を採用しない理由

- Docker Desktop は既知の選択肢である
- ただし、今回の導入ではライセンス面の確認事項を増やさずに進めたい
- そのため、WSL2 上の Linux 側 Engine を用いる構成とする

### 3.4 Windows 側でビルドする理由

- 古い Windows アプリでは、Windows 固有のビルド要件が発生しやすい
- .NET Framework、VB.NET、WinForms、古いプロジェクト形式などでは Windows 上でのビルドが安全である
- Visual Studio Build Tools、MSBuild、NuGet などを Windows 側に集約できる

### 3.5 NuGet を共有フォルダ運用とする理由

- 外部接続が限定的なため、毎回インターネットへ依存しない運用が必要
- 初期段階では社内共有フォルダ方式が比較的簡易に導入できる
- 将来的に必要であれば、社内 NuGet リポジトリ化を検討できる

---

## 4. 初期構成

### 4.1 構成概要

初期は 1 台構成とし、以下の役割を持たせる。

#### Windows ホスト側

- ビルド実行環境
- Visual Studio Build Tools
- MSBuild
- NuGet
- Gitea runner
- 共有 NuGet フォルダへのアクセス

#### WSL2 Linux 側

- Gitea
- 必要に応じて関連コンテナ

### 4.2 構成イメージ

```text
+------------------------------------------------------+
| Windows Host                                         |
|------------------------------------------------------|
| [Windows 側]                                         |
| - ビルド実行環境                                     |
| - Visual Studio Build Tools / MSBuild                |
| - NuGet                                              |
| - Gitea runner                                       |
| - 共有 NuGet フォルダへのアクセス                    |
|                                                      |
| [WSL2 Linux 側]                                      |
| - Gitea                                              |
| - Linux 側 Engine によるコンテナ実行環境            |
+------------------------------------------------------+
```

---

## 5. NuGet 運用方針

### 5.1 基本方針

- 初回は外部接続可能な環境で必要な NuGet パッケージを取得する
- ビルド確認後、使用するパッケージを共有フォルダへ登録する
- 閉域側では、共有フォルダのみを参照して restore / build を実施する

### 5.2 共有フォルダ運用の考え方

- 共有フォルダを NuGet source として扱う
- リポジトリ内 `NuGet.Config` により、共有フォルダのみを参照させる
- 通常のビルド環境からは共有フォルダを読み取り専用で利用する
- パッケージ追加は検証済みのものだけを登録する

### 5.3 今後の拡張余地

- 現段階では共有フォルダ方式で開始する
- 将来的にパッケージ数や利用プロジェクト数が増えた場合は、社内 NuGet リポジトリ化を検討する

---

## 6. 実証検証の目的

初期段階では、以下が成立することを確認する。

- WSL2 上で Gitea が安定して動作すること
- Windows 側でビルド実行環境が構築できること
- 共有 NuGet フォルダのみで restore が成立すること
- 古い Windows アプリのビルドが安定して実行できること
- 再起動後も運用を継続できること

---

## 7. 将来構成

将来的に予算確保できた場合は、ビルド実行環境を別 Windows マシンへ分離する。

### 7.1 分離後の想定

- Gitea は継続利用する
- ビルド実行環境のみを別 Windows マシンへ移す
- 必要に応じて署名や配布工程も分離する

### 7.2 分離の利点

- ビルド負荷と Git サーバー負荷を分離できる
- 運用上の障害切り分けをしやすくなる
- ビルド専用の権限設計がしやすくなる

---

## 8. 留意事項

- 初期の 1 台構成は、導入簡略化を優先した暫定構成である
- 長期的には役割分離を前提とする
- 共有 NuGet フォルダ運用は初期〜中期の現実的な方法として採用する
- ビルド対象が古い Windows アプリであるため、Windows ビルド前提を維持する

---

## 9. まとめ

本方針では、追加ライセンスや構築負荷を抑えつつ、古い Windows アプリ開発に必要なソース管理・ビルド環境を段階的に整備する。

初期は以下を前提とする。

- Gitea を採用する
- Windows 上の WSL2 Linux 環境で運用する
- Docker Desktop は採用せず、Linux 側 Engine を用いる
- ビルドは Windows 側で実施する
- NuGet は共有フォルダから供給する
- 初期は 1 台構成で実証検証を行う
- 将来的にビルド環境を分離する
